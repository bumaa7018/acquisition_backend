# Үр дүнг хэвээр хадгалах гүйцэтгэлийн оновчлолын төлөвлөгөө

Огноо: 2026-09-14

Зорилго: API-ийн оролт, хариу болон дэлгэцэд харагдах мэдээллийг өөрчлөхгүйгээр SQL-ийн давтан ажил, DB холболтын өрсөлдөөн, санах ойн хэрэглээг бууруулах. Энэ баримт нь хэрэгжүүлэх төлөвлөгөө; үйлдвэрлэлийн кодын өөрчлөлт биш.

Төлөв: эцэслэсэн. Хэрэгжүүлэгчид өгөх prompt: `docs/performance-optimization-gpt55-prompt.md`.

**Хамгийн өндөр эрэмбийн шаардлага: үр дүнгийн нийцэл нь хурдны зорилтоос давуу.** Ижил оролт, хэрэглэгчийн эрх, DB төлөв дээр бизнесийн хариу болон ажлын урсгал ижил байна. Үүнийг батлаагүй өөрчлөлтийг хурдан болсон шалтгаанаар хүлээн авахгүй. Одоогийн хэрэгжүүлэлт алдаатай мэт харагдсан ч буцааж байгаа мэдээлэл/зан төлөвийг энэ ажлаар засахгүй; тусдаа асуудал болгон тэмдэглэнэ.

## 1. Хэвээр хадгалах нөхцөл

- URL, HTTP method, query/body параметр, authentication/authorization болон байгууллага/хэрэглэгчийн өгөгдлийн хүрээ.
- HTTP status, JSON бүтэц, талбарын нэр/төрөл, null/хоосон массив, тоон нарийвчлал, одоо буцаж байгаа бүх мөр, total болон pagination metadata.
- Шүүлтүүр, үнэлгээний сонгосон урсгал, төлөв, soft-delete-ийн одоогийн семантик; оновчлолтой хамт бизнесийн логик засахгүй.
- Одоогийн ORDER BY болон түүний эрэмбэлэх дүрэм. Ижил эрэмбийн утгатай мөрүүдийн дараалал SQL-д тодорхойгүй бол түүнийг тусад нь тэмдэглэж, шинэ tie-breaker дур мэдэн нэмэхгүй.
- Бичих үйлдлийн commit/rollback, хэсэгчилсэн амжилт, түүх, audit, notification болон гадаад системд үзүүлэх нөлөө.
- Одоогийн synchronous үйлдэл бүр дууссаны дараа одоогийн хариугаа буцаана; frontend өөрчлөх шаардлагагүй.

Энэ хүрээнд хийхгүй зүйлс:

- `assets`-д одоо үл хэрэгжиж байгаа pagination-ийг идэвхжүүлж мөр хасах; compensation, snapshot, filter-options-д шинэ LIMIT тавих.
- `202 Accepted`, job ID, polling нэмэх; шинэ 429/503 эсвэл богино timeout-оор хурдыг сайжирсан мэт болгох.
- Хуучирсан дүн буцааж болох TTL cache, асинхрон materialized summary, ойролцоо COUNT ашиглах.
- Геометрийг хялбарчилж координат, огтлолцол, талбай эсвэл давхцлын босгыг өөрчлөх.

### Заавал мөрдөх баталгаажуулалтын дүрэм

- Оновчлолоос ӨМНӨ хуучин хэрэгжүүлэлтийг өөрчлөгдөхгүй reference болгон хадгална. Хуучин/шинэ кодыг тусдаа боловч ижил fixture-тэй DB дээр ажиллуулна; шинэ кодоос expected үр дүн үүсгэхгүй.
- Хариуны JSON object-ийн key дарааллыг үл тооцож болно. Array-ийн дараалал, давхардсан мөр, numeric утга, date/timezone, omitted/null/empty ялгааг арилгаж харьцуулахгүй. Эрэмбэ нь эх кодод тодорхойгүй массив/ижил sort утгатай мөрийн тогтворгүй байдлыг baseline дээр нотолж тусад нь тайлагнана; үүнийг далимдуулж бүх массивыг sort/set болгож харьцуулахгүй.
- Огноо, ID-г бүхэлд нь тестээс хасахгүй. Clock/ID үүсгэгчийг удирдах эсвэл үүссэн ID-ийн холбоос, тоо, бизнесийн огнооны утгыг тусад нь батална. Decimal SUM-ийг float нийлбэрээр сольж дугуйлалтыг өөрчлөхгүй.
- Бизнесийн нэг ч батлагдсан ялгаа гарвал тухайн өөрчлөлтийг засах эсвэл буцаана. Ялгааг зөвшөөрүүлэхээр хуучин expected/assertion-ийг сулруулахгүй. Бусад бие даасан, нийцэл нь батлагдсан ажлыг үргэлжлүүлж болно.
- Олон query-г нэг SQL болгох, шинэ lock/queue нэмэх, publication-ийг зэрэгцүүлэх нь concurrent write үед snapshot, харагдах хугацаа, error precedence, partial success-ийг өөрчилж болно. Read-only fixture дангаараа эдгээрийн нийцлийг батлахгүй. Concurrent write болон алдаа/цуцлалтын тест шаардана; батлагдаагүй бол хуучин transaction/ажлын дарааллыг хадгалсан хувилбарыг сонгоно.
- Frontend ажиллуулж шалгаагүй бол «дэлгэцийн үр дүн ижил гэдгийг бүрэн баталсан» гэж тайлагнахгүй. Backend contract-ийн шалгалт ба бодит UI/network шалгалтыг тусад нь тэмдэглэнэ.

## 2. Суурь хэмжилт ба үр дүнгийн хамгаалалт — P0

Хамрах файл: `internal/handler/http/router.go`, `internal/handler/http/land.go`, `internal/repository/postgres/land_acquisition_repo.go`, `internal/repository/postgres/decision_draft.go`.

1. Endpoint → handler → service → repository → SQL хамаарлыг жагсааж, `/prof/...` болон external хувилбаруудыг хамруулах.
2. Тогтмол fixture дээр хуучин ба шинэ хэрэгжүүлэлтийн HTTP хариуг харьцуулах integration test бэлдэх. Хоосон өгөгдөл, олон олговор/санхүүжилттэй мөр, null, сонгосон үнэлгээ, soft-delete, жил/байршил/роль, бүх ашигладаг sort/page нөхцөлийг хамруулах.
3. Хүнд SQL-д тусгаарласан DB дээр `EXPLAIN (ANALYZE, BUFFERS, SETTINGS)` авч, бодит мөр, loops, sort/hash spill, planning/execution хугацааг бүртгэх. Production дээр хүнд EXPLAIN ANALYZE шууд ажиллуулахгүй.
4. Нийт хүсэлтийн хугацаа, SQL-ийн тоо/хугацаа, pool wait, CPU, RSS, temporary disk usage, response bytes, алдааны тоог зэрэг хэмжих. Нууц өгөгдөл болон bind утгыг логт гаргахгүй.
5. Бичих урсгалын тестэд зөвхөн JSON бус DB-ийн эцсийн төлөв, түүх, audit болон external call-ийн тоог шалгах.

Өмнөх суурь: 100 чөлөөлөлт, 10,000 parcel, 30,000 compensation, 10,000 asset, 50,000 status history, 10,000 valuation submission. 10 зэрэгцээ repository дуудалтын дундаж/хамгийн удаан хугацаа: dashboard 3.00/6.87 сек; жилтэй dashboard 8.20/10.04 сек; summary 2.10/9.11 сек; download эхний 20 мөр 0.390/0.735 сек. Энэ нь ARM орчинд amd64 PostgreSQL image ашигласан локал хэмжилт; production болон HTTP-ийн бүтэн хугацаа биш.

## 3. Давтагдсан уншилт ба индекс — P1

Хамрах файл: `internal/service/land.go`, `internal/middleware/assignment.go`, `internal/repository/postgres/land_acquisition_repo.go`, шинэ migration.

- `IsAcquisitionLocked`, `AcquisitionStatus`-д зориулж зөвхөн `status` уншдаг repository method нэмнэ. Геометр, parcel count, AU, assignee татдаг `GetByID`-г эдгээр шалгалтаас хасна. Олдоогүй/устгасан мөрийн одоогийн алдааны зан төлөвийг хадгална.
- Зөвхөн байдаг эсэхийг шалгадаг service-д `EXISTS` эсвэл хамгийн бага projection хэрэглэнэ. Ижил хүсэлт дотор давтан уншилт арилгахдаа өмнөх middleware-ийн шалгалт болон transaction-ийн lock шаардлагыг алгасахгүй.
- Migration ба бодит DB-ийн индексийг тулгана. Доорхыг шууд бүгдийг нэмэхгүй; query plan-аар хэрэгцээг батална:
  - `parcel_status_history(parcel_id, status_date DESC)` — хамгийн сүүлийн огноо.
  - `compensation(acquisition_id, parcel_id, valuation_type)` — сонгосон урсгалын нэгтгэл; amount/target/asset талбарыг INCLUDE хийх зардлыг тусад нь үнэлнэ.
  - `assets(acquisition_id, parcel_id, valuation_type)` болон жагсаалтын sort-т тохирох индекс.
  - Идэвхтэй decision draft link, funding link, parcel status/count, plan suggest-ийн хайлтад тохирох индексүүд.
- Одоо байгаа trigram болон GiST индексийг давхар үүсгэхгүй. Шинэ индексийн диск, INSERT/UPDATE-ийн нэмэлт зардлыг хэмжинэ.

Гарах үр дүн: бизнесийн хариу өөрчлөгдөхгүй; төлөв шалгалт бүрийн олон SQL, WKT хөрвүүлэлт болон зарим давтагдсан scan арилна.

## 4. Dashboard ба тайлангийн нэгтгэл — P1

### Dashboard

- Шүүлтэд тохирох acquisition/parcel багцыг SQL дотор нэг удаа тодорхойлж, түүнийг ашигласан summary блокуудаар зохион байгуулна. Одоо нэг хүсэлтэд ажилладаг 9 query, 8 зэрэгцээ урсгалыг цөөлнө.
- Нийт parcel, чөлөөлсөн parcel, талбай, төлөвийн задаргааг нэг pass эсвэл `GROUPING SETS`-ээр гаргах хувилбарыг хэмжинэ.
- Жилийн шүүлтэд ашигладаг сүүлийн status_date-ийг дахин дахин correlated MAX хийхгүй. Шүүгдсэн parcel багцад нэгтгэх эсвэл индексээр хамгийн сүүлийн мөр авах аргын аль хурданыг сонгоно.
- Compensation-ийг acquisition/parcel/valuation_type түлхүүрээр урьдчилан нэгтгэж JOIN хийнэ. JOIN-оор мөр үржиж SUM/COUNT давхардахгүйг батална.
- Timeline, valuation, AU code болон гүйцэтгэлийн жагсаалт тус бүрийн ОДООГИЙН filter semantics-ийг тусад нь хадгална. Эдгээр нь кодод бүгд ижил шүүлттэй биш; нэг common filter рүү хүчээр оруулахгүй.
- Гүйцэтгэлийн хувиар эрэмбэлэх болон LIMIT 1000-ыг хэвээр хадгална. LIMIT-ийг aggregation-ийн өмнө шилжүүлж шилдэг 1000 мөрийг өөрчилж болохгүй.
- Том нэг SQL бүх тохиолдолд хурдан гэж үзэхгүй. Нэг SQL эсвэл 2–3 хязгаарлагдсан query хувилбарыг CPU/IO/p95-аар харьцуулж сонгоно. CTE reuse-ийг query plan-аар батална.

### Report summary

- Одоо 3 тусдаа query-д давтагддаг `parcel_agg`-ийг нэг SQL дотор нэг удаа гаргаж, нийт дүн, статус, жилийн задаргааг одоогийн DTO-д угсарна.
- Шаардлагатай үед `MATERIALIZED` эсвэл `GROUPING SETS` хэрэглэж, давтан scan үнэхээр буурсныг хэмжинэ.
- `COUNT(DISTINCT acquisition_id)`, ангилал тус бүрийн amount, null/default, жилийн логикийг яг хадгална.

### Report download

- Одоогийн шүүлтүүр, sort, page дүрмээр буцах мөрийн багцыг эхэлж тогтооно. Дараа нь зөвхөн тэр багцын compensation/assets-ийг нэгтгэнэ.
- Энэ шилжүүлэлтийг хийхийн өмнө JOIN бүрийн cardinality-г батална: parcel_detail/right_holder зэрэг холбоосын улмаас эцсийн мөр олширдог бол зөвхөн parcel ID-г түрүүлж хуудаслах нь үр дүнг өөрчилж болно. Тийм тохиолдолд одоогийн эцсийн мөрийн түвшинд page тогтоох эсвэл хуучин зохион байгуулалтыг хадгална.
- `total` нь бүх тохирох өгөгдлийн бодит тоо хэвээр байна. COUNT-ийг цөөн JOIN-той query-гаар гаргах боломжийг ашиглана.
- Гадаад API-г cursor pagination руу шилжүүлэхгүй. Том OFFSET-ийн үлдэх өртгийг хэмжиж тэмдэглэнэ.

## 5. Жагсаалт, захирамж, санах ой — P2

Хамрах endpoint: `/decision-drafts`, `/land-acquisitions`, `/:id/assets`, `/:id/compensations`, `valuation-snapshots`, `filter-options`, `/plans/suggest`, `/audit-logs`, `/client-requests`.

- Decision draft-ийн тухайн page-ийн ID-уудыг эхэлж авч, parcel/funding/compensation нэгтгэлийг багцаар гаргана. Мөр бүрийн олон nested subquery-г арилгана. Одоогийн санхүүжилтийн ангилал, string aggregation-ийн дарааллыг хадгална.
- Acquisition-ийн тухайн page-д хэрэгтэй parcel count/final count/overlap count-ийг багцаар гаргана. `sort_by=parcel_count` үед page-ээс өмнө зөв тоогоор эрэмбэлэх шаардлагыг хадгална.
- Хуудаслалтгүй assets, compensation, snapshot, dropdown-ийн буцах мөрийг хасахгүй. Индекс, зөв projection, шаардлагагүй entity→DTO давхар хуулбар болон JSON decode/encode-ийг багасгана.
- Snapshot-ийн nested JSON-ийг боломжтой хэсэгт raw JSON хэлбэрээр дамжуулна; JSON-ийн бүтэц, утга, тоон нарийвчлалыг тестээр хамгаална.
- Бүтэн хариуг client руу хэсэгчлэн бичиж эхэлснээр дараагийн SQL алдаанд өмнөх HTTP error буцаах боломж алдагдах ёсгүй. Шууд streaming хийхгүй; buffered/spooled хувилбар хэрэгтэй эсэхийг хэмжилтээр шийднэ.
- `plans/suggest`-ийн wildcard хайлт болон WKT хөрвүүлэлтийг query plan-аар шалгана; одоо буцаадаг geometry талбарыг дур мэдэн хасахгүй.
- Audit/client-request жагсаалтад filter/sort индекс, нарийн projection болон COUNT-ийн өртгийг шалгана. Одоогийн request/response body талбаруудыг хасахгүй.

Үлдэх хязгаар: бүх мөрийг буцаах шаардлагатай API-ийн сүлжээний хэмжээ өгөгдөлтэйгээ хамт өснө. Индекс нэмэх нь буцаах байтын хэмжээг багасгахгүй; энэ зардлыг бүрэн арилгахын тулд API гэрээ өөрчлөх шаардлагатай тул энэ төлөвлөгөөнд орохгүй.

## 6. Таталт, импорт, геометр, GeoServer — P2

### Parcel discovery ба sync

- Гадаад API-ийн одоогийн 100 мөрийн багц, cursor, pause, нийт хязгаарыг хадгална.
- `InsertParcelCodes`-ийн байгаа/шинэ мөрийн шалгалтыг багцаар хийнэ. Batch SQL/staging/COPY хувилбарыг хэмжиж, одоогийн duplicate, өөр acquisition-ийн эзэмшил, геометрийн fallback болон history үүсэх дүрмийг хадгална.
- Одоогийн хэсэгчилсэн амжилтын зан төлөвийг нэг том transaction-оор санамсаргүй all-or-nothing болгохгүй. Алдаатай мөрийг салгах fallback-тай bounded batch хэрэглэнэ.
- Таталтын явцад шууд бичиж эхлэх нь одоогийн алдаа/цуцлалт/хил өөрчлөлтийн зан төлөвт нөлөөлөх эсэхийг батална. Батлагдаагүй бол fetch-then-write дарааллыг хадгалж, санах ойг spool/bounded representation-аар бууруулна.
- Sync-ийн баримт, эзэмшигч зэрэг lookup/upsert-ийг багцалж болох хэсгийг нэгтгэнэ. External request concurrency-г хязгаарлаж, одоогийн файл/notification/audit нөлөөг хадгална.

### Геометрийн давхцол

- GiST/bounding-box нөхцөлөөр candidate pair-ийг багасгана. Геометрийн `ST_MakeValid`-ийг нэг ажилд талбар бүрээр урьдчилан тооцож дахин ашиглана.
- Одоогийн raw geometry дээрх `ST_Intersects` болон valid geometry дээрх intersection/UTM area логикийн ялгааг хэвээр хадгална; candidate selection-ийн семантикийг өөрчлөхгүй.
- Ижил acquisition-д давхардсан тооцоог зэрэг явуулахгүйгээр request дотор хүлээлгэнэ. Multi-instance орчинд transaction/advisory lock-ийн scope, lock order-ийг тодорхойлно.
- Эхний хувилбарт бүтэн recomputation-ийг хадгална. Зөвхөн өөрчлөгдсөн талбарыг тооцох incremental хувилбар нь `detected_at`, түүх болон үр дүнг өөрчилж болзошгүй тул тусдаа equivalence нотолгоогүйгээр оруулахгүй.
- Бүх геометр давхцсан муу нөхцөлд хосын тоо N² хэвээр өсөх боломжтой; индексээр энэ математик хязгаарыг бүрэн арилгах боломжгүй.

### Valuation import ба snapshot үүсгэх

- Asset/spec/calculation/compensation INSERT-уудыг одоогийн transaction дотор багцална. Asset ID, calculation sort_index, нэрээр үүсгэдэг төрөл, replacement cleanup болон rollback дүрмийг хэвээр хадгална.
- Calculation type-ийн давтагдсан нэрийн lookup-ийг нэг импортын хүрээнд дахин ашиглана.
- Valuation status-ийн snapshot үүсгэх nested JSON aggregation-ийг урьдчилан нэгтгэж, lock барих хугацааг багасгана. Snapshot нь lock авсны дараах зөв өгөгдлийг агуулж байгааг батална; concurrent өөрчлөлтөөс зөрөх precompute хэрэглэхгүй.

### Drone refresh

- Нэг хүсэлт дотор бүх зургийн ажлыг дуусган хуучин response-оо буцаана. Зураг бүрийн header read/configure/publish-ийн давхардлыг багасгана.
- GeoServer Reset-ийг зураг бүрээс нэг refresh-ийн төгсгөлд нэгтгэх нь external call-ийн тоо болон publication visibility-г өөрчилдөг тул үндсэн хэрэгжүүлэлтэд оруулахгүй. Тусдаа зан төлөвийн өөрчлөлтийн санал болгон үлдээнэ.
- Publication-ийг хязгаарлагдсан concurrency-тай ажиллуулах эсвэл дарааллыг хэвээр үлдээхийг GeoServer-ийн хэмжилтээр сонгоно.

## 7. Ачааллын удирдлага — P2

Хамрах файл: `cmd/api/main.go`, dashboard/report service/repository.

- SQL-ийг хөнгөлсний дараа DB pool-ийн 30 холболтыг шууд өсгөхгүй; CPU/IO болон бусад API-ийн pool wait-аар тохируулна.
- Хүнд уншилтуудад bounded admission queue/semaphore хэрэглэх туршилт хийнэ. Хүсэлт одоогийн request context-ийн хүрээнд хүлээж, ижил хариу авна; энэ ажлаар шинэ rate-limit response нэвтрүүлэхгүй.
- Хүнд ажлын permit хүлээх үед DB connection барихгүй. Бусад API болон background log-ийн хэрэгцээнд холболтын нөөц үлдээхээр хэмжинэ.
- Cache-гүй query оновчлолыг эхэлж хэрэгжүүлнэ. Cross-request singleflight/cache нь authorization scope, шинэ бичлэгийн харагдах хугацаа, cancellation-д нөлөөлөх тул үндсэн шийдэл болгохгүй.
- Query-д request cancellation зөв дамжиж, rows/transaction/connection үргэлж чөлөөлөгдөхийг шалгана. Урт хугацааны хамгаалалтын шинэ timeout/queue rejection бодлого нь API-ийн алдааны зан төлөв өөрчилдөг тул энэ хүрээнд идэвхжүүлэхгүй.

## 8. Баталгаажуулалт ба нэвтрүүлэх дараалал

1. P0: хуучин хариу болон DB үр дүнгийн fixture, baseline, query plan.
2. P1-A: төлөв/exists-ийн хөнгөн query, батлагдсан индексүүд.
3. P1-B: dashboard болон summary-ийн давтагдсан нэгтгэл.
4. P1-C: report download, decision draft, acquisition list.
5. P2-A: хуудаслалтгүй жагсаалтын memory/serialization, import/discovery batching.
6. P2-B: geometry, snapshot creation, GeoServer refresh.
7. P2-C: concurrency tuning, бүрэн HTTP болон холимог урсгалын тест.

Үе шат бүр тусдаа reviewable өөрчлөлт байна. Үр дүнгийн ялгаа гарвал дараагийн шат руу орохгүй. Индекс нэмэхийг одоогийн migration runner-ийн transaction дэмжлэгтэй тулгаж, production-д урт write lock үүсгэхгүй concurrent build арга хэрэглэхээр тусад нь бэлдэнэ. Additive migration ашиглаж, хуучин код руу rollback хийх боломж хадгална.

Хүлээн авах шалгуур:

- Тогтмол DB snapshot дээр хуучин/шинэ API хариу болон бичих үйлдлийн DB үр дүн ижил. Зөвхөн хугацаа, санамсаргүй ID зэрэг динамик талбарыг тестэд хяналттай тогтмолжуулна; бизнесийн өөрчлөлтийг нуух normalize хийхгүй.
- Бодит HTTP-ээр 1, 10 зэрэгцээ хэрэглэгч; дан endpoint болон нэг дэлгэцийн олон хүсэлттэй холимог хувилбарыг шалгана. Frontend код энэ репод байхгүй тул бодит request mix-ийг browser/network trace эсвэл frontend репогоос тогтооно.
- Ижил dataset дээр warm/cold cache, эхний/гүн page, шүүлтгүй/жилтэй/эрхийн хүрээтэй хувилбаруудыг тусад нь харьцуулна. 10 зэрэгцээ горимд дор хаяж 300 хүсэлтээр p50/p95/p99, алдаа, throughput-ийг хэмжинэ; удаан query гарвал тестийн тусдаа safety cutoff хэрэглэж, timeout-уудыг амжилттай хугацаанд тооцохгүй.
- Эхний гүйцэтгэлийн зорилт: өмнөх 10,000 parcel fixture дээр хүнд уншилтын p95-ийг дор хаяж 50% бууруулах, алдааны тоог нэмэхгүй байх. Энэ нь баталгаатай амлалт биш; production SLA-г бодит сервер/өгөгдлөөр тогтооно.
- Хөнгөн API-ийн p95-ийг хүнд хүсэлтийн зэрэгцээ хэмжиж, өөрчлөлтөөс болж регресс үүсээгүйг батална. Query-ийн тоо буурсан ч CPU/temporary disk/RAM нэмэгдвэл сайжруулалт гэж хүлээн авахгүй.
- Production хэмжээтэй төлөөлөх өгөгдөл, олон түүх/олговортой parcel, нягт давхцсан геометр, concurrent import/write нөхцөлийг тусгаарласан орчинд шалгана.

Бүх мөрийг буцаах API-ийн хариуны хэмжээ, бүх талбар давхцах геометрийн хосын тоо, гадаад системийн хариу өгөх хугацааг зөвхөн дотоод SQL оновчлолоор бүрэн арилгах боломжгүй. Эдгээрийн үлдсэн өртөг болон хэмжсэн хязгаарыг эцсийн тайланд тусгана.

## 10. Гүйцэтгэлийн бүртгэл — P1-B (давтагдсан нэгтгэл)

Энэ шатанд SQL-ийг ДАХИН БИЧСЭН тул §9.1-ийн тэнцүү байдлын харьцуулагч
заавал ажиллана. Эталоныг оновчлолын ӨМНӨХ кодоор бичиж авсан
(git HEAD + §9.4-ийн `sort.Strings` засвар), дараа нь шинэ кодыг түүнтэй
тулгасан.

### 10.1 `GetDashboard` — чөлөөлөлтийн шүүлтийг 8 удаа биш 1 удаа бодох

Дашбоард нь 8 асуулгыг горутинаар зэрэг явуулдаг ба тэдгээр бүрд
чөлөөлөлтийн бүтэн `WHERE`-ийг дэд асуулга болгон шигтгэдэг байв. Жилийн
шүүлт нь дотроо нэгж талбар бүрийн сүүлийн статусын огноог олдог тул тэр
ажил 8 дахин давтагдана.

Одоо `SELECT la.id ... WHERE <шүүлт>`-ийг НЭГ УДАА ажиллуулж, гарсан
id-уудыг `= ANY($1::uuid[])` байдлаар 8 асуулгад дамжуулна.
`la.id IN (<шүүлт>)` ба `la.id = ANY(<тэр шүүлтийн үр дүн>)` нь ижил олонлог.

Хэрэгжүүлэхэд гарсан хоёр зүйл:

- PostgreSQL нь **хэрэглэгдээгүй параметр** дамжуулахыг зөвшөөрдөггүй
  (`expected 1 arguments, got 3`). Чөлөөлөлтийн жагсаалтын болон
  захиргааны нэгжийн асуулга нь оны параметр хэрэглэдэггүй тул асуулга
  тус бүрд яг хэрэглэх параметрээ өгдөг болгов (`buildParcelScope`).
  Энэ алдааг тэнцүү байдлын харьцуулагч шууд барив.
- Мэргэжлийн байгууллагын салаа fixture-д өгөгдөлгүй байсан тул эталонд
  ОГТ хамрагдахгүй байлаа. Fixture-т `professional_org_id` (25 чөлөөлөлт)
  ба `independent_org_id` (475 талбар) нэмж, 3 хувилбар нэмэв — тэдгээр нь
  параметрийн дугаарлалт зөв эсэхийг шалгана.

### 10.2 `GetReportSummary` — ижил CTE-г 3 удаа биш 1 удаа

`parcel_agg` CTE (нэгж талбар бүрд сүүлийн статусын огноо + compensation,
assets руу JOIN) нь нийлбэр, төлөвийн задаргаа, жилийн задаргаа гэсэн
ГУРВАН тусдаа асуулгад давтагддаг байв.

Одоо гурвуулаа нэг асуулга: `by_status`, `by_year` дэд CTE болж, задаргаанууд
`json_agg(... ORDER BY ...)` баганаар нэг мөрөнд ирнэ. PostgreSQL 12+ дээр
хоёроос олон удаа лавласан CTE нь inline хийгдэхгүй тул `parcel_agg` нэг л
удаа materialize хийгдэнэ.

Хадгалсан нарийн зан төлөв: задаргаа хоосон үед талбарууд `nil` хэвээр
үлдэнэ (хоосон массив биш) — эс бөгөөс JSON хариу `null`-аас `[]` болж
өөрчлөгдөнө. Үүнийг `report_summary_none` хувилбараар барьж байна.

### 10.3 Хэмжилтийн арга

Нэг ажиллуулалт хангалтгүй: код нь ОГТ өөрчлөгдөөгүй хувилбарууд ч
ажиллуулалт хооронд 10x p95 дээр ±60% хүртэл хэлбэлзэж байв (нэг локал
контейнер, ARM дээрх amd64 image). Тиймээс хуучин/шинэ кодыг ээлжлүүлэн
**3 хос давталтаар** хэмжиж медианыг авна. Код хөндөөгүй хувилбарыг
(жишээ нь `report summary` нь dashboard-ийн засварын үед) шуугианы
хэмжүүр болгон ашиглана.

### 10.4 Хэмжсэн үр дүн

3 хос давталтын **медиан** (perfdb, 1x = 10 дуудлага, 10x = 30 дуудлага).
`dashboard+жил` нь §9.3-ийн индекс аль хэдийн суусан байдал дээр хэмжигдсэн
тул энэ нь ЗӨВХӨН §10.1-ийн дахин бичилтийн нэмэлт өгөөж:

| хувилбар | 1x хуучин | 1x шинэ | Δ | 10x p95 хуучин | 10x p95 шинэ | Δ |
|---|---|---|---|---|---|---|
| dashboard + жил | 335 мс | 224 мс | **−33%** | 2.90 с | 1.33 с | **−54%** |
| report summary | 205 мс | 111 мс | **−46%** | 630 мс | 423 мс | **−33%** |
| dashboard (жилгүй) | 67 мс | 69 мс | өөрчлөлтгүй | 734 мс | 680 мс | шуугианы дотор |

`dashboard` (жилийн шүүлтгүй) өөрчлөгдөөгүй нь хүлээгдсэн: шүүлт хөнгөн
үед түүнийг 8 удаа бодох нь бараг зардалгүй. Ашиг нь зөвхөн ХҮНД шүүлттэй
үед гарна.

Нийт зам (индекс + дахин бичилт хоёулаа) дээр жилийн шүүлттэй дашбоард:
**30 сек+ timeout → 224 мс** (1 хэрэглэгч).

### 10.5 Хийгээгүй зүйл ба үлдсэн эрсдэл

- `acqIDs` массив нь хязгааргүй: чөлөөлөлт олон мянга болвол uuid массив
  8 асуулгад дамжина (5,000 id ≈ 80 КБ × 8). Одоогийн хэмжээнд асуудалгүй ч
  production-д чөлөөлөлтийн тоо огцом өсвөл дахин үнэлэх хэрэгтэй.
- `parcelYearCond` (нэгж талбар бүрийн сүүлийн статусын он) нь одоо ч 6
  асуулгад давтагдана. §9.3-ийн индексийн дараа энэ нь index-only scan
  болсон тул давуу зорилт биш болов; дараагийн ээлжинд авч үзнэ.
- `ListReportParcels` нь COUNT + хуудасны хоёр асуулгатай — энэ нь ердийн
  хуудаслалт тул давтагдсан нэгтгэлд тооцогдохгүй, хөндөөгүй.
